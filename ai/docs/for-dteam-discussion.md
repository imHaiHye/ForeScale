# 🟢 [C팀 → D팀] `/predict` 자동 호출 주체 논의

> **결정 필요 시점**: 4주차 통합 직전 (3주차 말까지)
> **결정 항목**: "C팀 `/predict`를 누가, 어떻게, 얼마나 자주 호출할 것인가"
> **현재 상태**: `/predict` 엔드포인트 자체는 완성 — 누군가 호출하면 예측 + 알람 전송까지 자동 완결됨

---

## 1️⃣ 논의 배경

### 현재 구현 상황
C팀 `/predict` 엔드포인트는 호출 한 번에 다음을 모두 처리해요:

```
요청 1회 → [Prophet_CPU 예측 + Prophet_Traffic 예측 + Spike 감지
          → OR 트리거 판단 → 위험 시 D팀에 자동 알람 POST] → 응답
```

### 비어있는 부분
**"누가 매 1분마다 이 엔드포인트를 호출할 것인가?"** 가 아직 정해지지 않았어요.

기획 단계에서 *"FastAPI가 Prometheus를 주기적으로 호출"* 이라고 적혀있지만, 구체적으로 어디서 그 "주기적" 트리거가 시작되는지 합의가 필요해요.

---

## 2️⃣ 옵션 비교

### 🅰️ 옵션 A — C팀 FastAPI 내부 스케줄러

```
┌────────────────────────────────────────────┐
│  C팀 AI VM (FastAPI)                       │
│  ┌──────────────────────────────────────┐  │
│  │ 백그라운드 스케줄러 (매 1분 자동 실행)  │  │
│  │   1. Prometheus에서 메트릭 fetch       │  │
│  │   2. /predict 내부 호출               │  │
│  │   3. 위험 시 D팀에 POST               │  │
│  └──────────────────────────────────────┘  │
└────────────────────────────────────────────┘
                        │
                        ▼ (위험할 때만)
              [D팀 Spring Boot]
              POST /alerts/scale-out
```

| 항목 | 내용 |
|---|---|
| 작업 주체 | C팀만 |
| 추가 작업량 | C팀: APScheduler 추가 (~30줄), D팀: 0 |
| 기획서 부합도 | ✅ "AI VM의 FastAPI가 Prometheus를 주기적으로 호출" 그대로 |
| 합의 변경 | 없음 (스펙 그대로) |
| 단일 책임 | C팀 = 예측·판단·자동 트리거 전체 책임 |
| 장애 격리 | C팀 FastAPI 다운 = 예측 자체 정지 (D팀 영향 없음) |
| 디버깅 | C팀 로그 한 곳만 보면 됨 |

| 항목 | 내용 |

### 🅲 옵션 C — D팀 Spring Boot에서 Pull

```
┌─────────────────────────────┐         ┌─────────────────────────┐
│  D팀 App VM (Spring Boot)   │   POST  │  C팀 AI VM (FastAPI)    │
│  ┌────────────────────────┐ │ ──────> │                         │
│  │ @Scheduled(매 1분)      │ │         │   /predict              │
│  │   /predict 호출         │ │ <────── │   → 예측 + 알람 자체    │
│  │   응답에 alert 있으면   │ │  응답   │     송신 (옵션 A/B처럼) │
│  │   자체 scale-out 실행   │ │         │                         │
│  └────────────────────────┘ │         └─────────────────────────┘
└─────────────────────────────┘
```

| 항목 | 내용 |
|---|---|
| 작업 주체 | D팀 (스케줄러), C팀 (응답 포맷 변경) |
| 추가 작업량 | D팀: `@Scheduled` + 메트릭 fetch + 응답 파싱, C팀: alert_sender 제거하고 응답에 trigger 정보 포함 |
| 기획서 부합도 | ⚠️ 흐름이 역방향 — "AI가 컨트롤러에 보고" → "컨트롤러가 AI에 질의" |
| 합의 변경 | ✅ **합의된 스펙 무효화 필요** (현재 스펙: C→D POST. C는 응답만 반환하게 바뀜) |
| 단일 책임 | 컨트롤러 흐름이 D팀 중심으로 명확 |
| 장애 격리 | C팀 다운 시 D팀이 직접 감지 가능 |
| 디버깅 | D팀 컨트롤러 로그에서 전체 흐름 추적 |

## 4️⃣ ⭐ C팀 추천: **옵션 A**

### 추천 이유 세 가지

**1) 합의된 스펙을 안 건드려도 된다**
현재 `api-spec-for-cteam.md` 그대로 유지. D팀은 받는 쪽 로직(`POST /alerts/scale-out`)만 만들면 됨. 추가 합의 회의 불필요.

**2) 기획서 그대로**
*"AI VM의 FastAPI가 Prometheus API를 주기적으로 호출"* — 이 한 문장이 곧 옵션 A의 정의. 발표 슬라이드도 수정 안 해도 됨.

**3) D팀 부담 제로**
D팀은 *"Spring Boot가 POST 요청 받으면 boto3 호출"* 만 집중. 이게 D팀의 핵심 가치 영역. 스케줄링·메트릭 fetch는 C팀이 가져감.

### 구현 계획 (4주차 작업)
- C팀 FastAPI에 `APScheduler` 라이브러리 추가
- 부팅 시 백그라운드 잡 등록: 매 1분 → Prometheus에서 직전 N분 데이터 fetch → 내부 `/predict` 호출
- ai-vm에서 Prometheus VM으로 HTTP 접근 가능한지 A팀(박세웅)에게 확인 (보안 그룹)

### 옵션 A 채택 시 D팀이 해야 할 일
👉 **사실상 없음.** 현재 합의된 스펙으로 `POST /api/v1/alerts/scale-out` 구현만 진행하면 됨.

## 5️⃣ 옵션 C 채택 시 어떻게 변경되는지 (참고용)

만약 D팀에서 "우리가 호출하는 게 더 맞다"고 판단할 경우 변경 사항:

### 스펙 변경
**기존 (현재 합의)**:
```
C팀 → D팀: POST /alerts/scale-out (위험할 때만)
```

**옵션 C 시**:
```
D팀 → C팀: POST /predict (매 1분)
C팀 응답에 trigger 정보 포함
D팀이 응답 보고 자체 boto3 호출
```

### 영향
- C팀: `alert_sender.py` 제거, `/predict` 응답에 `should_scale_out`, `severity` 등 필드 추가
- D팀: 1분 스케줄러 추가, C팀 응답 파싱 로직, cooldown 처리는 그대로
- 기획 발표 슬라이드: "AI가 컨트롤러에 알람" → "컨트롤러가 AI에 질의" 로 흐름 수정

→ **공수가 양쪽 모두 늘어남.** 옵션 A 대비 명확한 장점이 보이지 않는 한 비추천.

## 6️⃣ 결정 요청 사항

D팀(황준하)에게 두 가지만 확인 부탁드려요:

1. **옵션 A 동의 여부**: C팀이 자체 스케줄러로 매 1분 자동 호출 + 위험 시 현재 합의된 스펙대로 D팀에 POST. 이대로 진행해도 되는지?
2. **cooldown 상태 저장 위치**: 5분 cooldown 락이 메모리에 있는지, DB(SQLite)에 있는지. → Spring Boot 재시작 시 cooldown 초기화 여부 알려주시면 C팀 재시도 로직에 반영하겠음.

답변 주시는 대로 4주차 통합 작업 진행하겠습니다.
